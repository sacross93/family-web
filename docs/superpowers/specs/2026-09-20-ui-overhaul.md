## 네 개의 렌즈 — 같은 화면을 다르게 본다

문제 13개는 목록일 뿐이다. 무엇을 먼저 고칠지는 렌즈가 정한다.

**① 쓰는 순간.** 마트에서 카트를 밀며 한 손으로 장보기. 병원 대기실에서 아기 기록.
소파에서 저녁에 사진과 게시판. 책상에서 주말에 계획과 앨범 정리.
→ 폰에서 하는 일은 대부분 **보기와 체크**고, 긴 입력은 책상에서 한다.
그런데 지금은 폰에서도 모든 페이지가 **입력 폼을 먼저** 보여준다(문제 12). 거꾸로다.

**② 엄지.** 390×844 폰에서 한 손 엄지가 편히 닿는 곳은 화면 아래 3분의 1이다.
지금 네비게이션도 위(햄버거), 주요 액션(`+ 추가`)도 위, 페이지 제목도 위에 있다.
아래쪽 3분의 1은 FAB 두 개가 콘텐츠를 가리는 데만 쓰인다(문제 1·2).

**③ 누가.** 관리자는 한 명이고 나머지 가족은 읽고 쓰기만 한다.
`꾸미기` FAB 은 이미 **관리자에게만** 뜬다(`app-shell.tsx`) — 대부분의 가족에게 FAB 은 `물어보기` 하나다.
그러니 가리는 문제를 풀려고 `물어보기`를 건드릴 필요가 없다. **`꾸미기`를 FAB 층에서 빼면 된다.**

**④ 얼마나 자주.** 매일 = 홈·할일·장보기. 주 단위 = 캘린더·아기·게시판.
가끔 = 사진첩·기념일·계획. 드물게 = 관리자.
→ 탭 순서와 홈 카드 순서의 근거. 빈도가 낮다고 없애는 게 아니라, **한 단계 안으로** 넣는다.

## 방향

### 아래쪽 가장자리를 한 곳에서 정한다

폰 하단은 탭바·`물어보기` FAB·콘텐츠 여백·iOS 안전영역이 서로 밀어내는 자리다.
페이지마다 따로 맞추면 또 가린다. `components/app-shell.tsx` 가 CSS 변수 하나로 정하고,
FAB 과 `main` 의 아래 여백이 **그 값을 읽는다**.

```
--bottom-bar : 탭바 높이 + env(safe-area-inset-bottom)   (lg 에서는 0)
물어보기 FAB : bottom = var(--bottom-bar) + 12px
main 아래 여백: var(--bottom-bar) + FAB 높이 + 여유
```

### 바꾸는 것

1. **폰 하단 탭바.** `getNav()` 의 **앞 4개 + 더보기**. 두 번째 목록을 만들지 않는다 —
   `NavItem` DB 오버라이드와 꾸미기 표면이 모두 NAV href 를 기준으로 돌기 때문이다.
   순서는 `lib/nav.ts` 한 줄이라 언제든 바꿀 수 있다. 렌즈 ④로 정한 앞 4개:
   **홈 · 할일 · 장보기 · 사진첩**. `더보기`는 **지금 있는 드로어**를 연다(나머지 5개 + 관리자 + 로그아웃).
2. **`꾸미기`를 FAB 층에서 뺀다.** 관리자 전용·가끔 쓰는 기능이라 페이지 헤더 안으로.
   계획 히어로의 ✨ 버튼(embedded 표면)은 그대로 둔다.
3. **폰 상단바가 현재 페이지를 말한다.** 모든 페이지에서 "포동 / 우리 가족 공간"을 반복하는 대신
   그 페이지의 이모지+제목을. `PageHeader` 의 설명은 `hidden lg:block`. 문제 5의 대부분이 여기서 준다.
4. **빈 것은 자리를 덜 차지한다.** 홈에서 비어 있는 카드는 한 줄로 접고 추가 버튼만 남긴다.
5. **기념일은 목록 하나.** 위 3건을 크게, 나머지는 이어서. 같은 항목을 두 번 싣지 않는다.
6. **항목 액션을 모은다.** 폰에서 항목당 아이콘 2~4개 대신 `…` 하나.
   AGENTS.md 의 "hover 로만 뜨는 액션 금지"는 지킨다 — 숨기는 게 아니라 **합치는** 것이다.
7. **목록이 먼저, 입력은 아래.** 게시판·장보기의 폼은 접거나 하단 고정 한 줄로.
8. **폰 달력은 격자 대신 일정 목록**(주 단위)으로. 격자는 lg 에서.
9. 계획 히어로 세로 정렬(문제 10) · 드로어 Escape(8) · 데스크톱 사진 줄 잘림(9) · 아기 날짜 입력(13).

### 바꾸지 않는 것

팔레트·타이포·모서리·그림자 토큰, 6색 분류, 냉장고 문 컨셉, URL, 데이터 패턴.
`/admin`(관리자 전용, 4.1화면)은 이번 개편 대상이 아니다.

### 순서 — 한 조각씩, 각각 커밋·테스트·양쪽 폭 확인

`ui-before-redesign` 태그가 바닥이고, 조각마다의 커밋이 더 촘촘한 되돌림 지점이 된다.

1. 앱 셸 — 탭바 · 상단바 제목 · FAB 재배치 · 하단 여백 일원화 · Escape. (DESIGN.md·AGENTS.md 같이 갱신)
2. 홈 — 빈 섹션 접기 · 오늘 먼저 · 데스크톱 사진 줄.
3. 기념일 — 목록 하나 · 항목 액션 패턴을 여기서 만들어 나머지에 쓴다.
4. 장보기·할일 — 목록 먼저, 입력은 하단.
5. 게시판·계획 상세·아기·캘린더.

**다음에도 이 순서로.** 로컬 시드는 깨끗해서 아무것도 안 알려 준다.
배포본을 폰 폭으로 열고, 떠 있는 것을 눌러 보는 쪽이 목록에 남은 어떤 손질보다 낫다.

### 두 번 겪고 알게 된 것 — 떠서 겹치는 것은 제자리에 그리지 않는다

`…` 메뉴가 카드의 `overflow-hidden` 에 잘려 **아래 항목을 아예 누를 수 없던 일**이
계획 상세와 할일에서 잇따라 났다. 처음에는 그 카드의 overflow 를 옮겨 막았는데,
카드마다 손보는 식으로는 다음 자리에서 또 난다. 지금은 메뉴를 `document.body` 로
내보내고(portal) 버튼 위치를 재서 띄운다 — 조상의 overflow 도 게시판 쪽지의
transform 도 상관없다. **앞으로 메뉴·툴팁·팝오버는 portal 로.**

검사가 이걸 놓친 이유도 적어 둔다: 그때 `/todos` 에 오늘 할일이 하나도 없어
`…` 버튼 자체가 없었다. **빈 화면은 아무것도 증명하지 못한다.**

| 아기 기록 | 있음(교환일기·검진) |
| 계획 | 1 (발리, 준비물 51개) |
| 일정 | 1 |
| 앨범 · 할일 · 장보기 · 기념일 · 게시판 | **전부 0** |

내가 정한 탭은 홈 · 할일 · 장보기 · 사진첩이었다 — **넷 중 셋이 빈 곳**이었다.
"가족 사이트라면 대개 이렇겠지" 하고 정한 것이지 이 가족을 보고 정한 게 아니었다.
지금은 홈 · 아기 · 장보기 · 계획. 장보기만 0인데도 남겼다 — 데이터가 시킨 게 아니라
지난 조각에서 한 화면에 들어오게 고쳤으니 이제는 쓸 만하리라는 **기대**다. 아니면 빼면 된다.

**가장 많이 쓰는 건 포동이다.** 대화 아홉 번 대 할일 0. 화면에서는 우하단의
작은 흰 알약 하나뿐이다.


### 세 번째로 배운 것 — 보는 것과 쓰는 것은 다르다

아기 페이지를 여러 번 **봤지만** 한 번도 **쓰지** 않았다. 기록을 남겨 보니 저장은 되는데
고치기가 안 됐다. 기록의 `…`(x 321–353, y 723–755)와 우하단 `물어보기` FAB(x 261–374,
y 726–776)이 겹쳐 있었고, 그 한가운데의 최상위 요소는 FAB 이었다 —
**일기를 고치려고 누르면 AI 채팅이 열렸다.**

내가 검사에서 "스크롤 도중 가려지는 건 정상" 이라 넘긴 것이 원인이다. 글자에는 맞는
말이지만 버튼에는 아니다: 글은 스쳐 지나가면 그만이고 버튼은 그 자리에서 누르면
**다른 것이 눌린다.** 검사를 고치니 사이트 전체에서 9건이 나왔다.

이제 떠 있는 것은 하단 탭바뿐이다(화면 가장자리, 모든 모바일 앱의 약속).
`포동이` 는 탭바 안·사이드바 위로 들어갔다. AGENTS.md 에 규칙으로 적었다.


### 화면은 보는 것으로 끝나지 않는다 — 검사가 두 벌인 이유

`npm run ui:audit` 은 **보이는 것**을 잰다(가로 스크롤·가려짐·메뉴 잘림).
`npm run ui:flows` 는 **눌러 본다**(만들고·고치고·지우고, 새로고침 뒤에도 그대로인지).
후자가 없으면 못 찾는 것들:

| 무엇 | 어떻게 드러났나 |
|---|---|
| 일기를 고치려면 AI 채팅이 열렸다 | `…` 가 떠 있던 버튼에 덮여 있었다 |
| 아래로 내려간 채 `…` 를 누르면 아무 일도 안 일어났다 | 메뉴가 열리자마자 스크롤에 스스로 닫혔다 |
| 이름 없는 체크박스 세 곳 | 스크린리더에 "체크박스" 라고만 |

`ui:flows` 는 로컬이 아니면 스스로 거부한다 — 실제로 만들고 지우기 때문이다.


올린 파일이 남는 갈래는 이제 다 막혔다: **사진·앨범·글 속 사진·스티커** 넷.

### "삭제" 라고 했으면 지워져야 한다

사진을 지우면 DB 행만 사라지고 **파일은 남아 있었다.** 배포에서는
무료 용량(Vercel Blob)을 계속 먹고, 주소를 아는 사람은 "지운" 가족 사진을 그대로 본다.

지금은 **파일을 먼저 지우고 행을 지운다.** 순서가 중요하다 — 행을 먼저 지우면
파일 삭제가 실패했을 때 어느 파일이었는지조차 모르는 고아가 남는다. 못 지우면
502 와 "사진 파일을 못 지웠어요" 를 돌려주고 행은 그대로 둔다.

**배포에서 실측했다**(2026-09-20): 사진을 올려 `HEAD` 200 · 94바이트를 확인하고,
앨범을 지운 뒤 2초 만에 **404**. blob 삭제 경로가 실제로 돈다.
(로컬 `unlink` 경로는 `ui:flows` 가 파일 개수로 매번 확인한다.)


### 글 안의 사진 — 방향이 반대인 이유

게시판·아기 기록·계획 설명에는 글 안에 사진을 넣을 수 있는데(MarkdownEditor),
앨범에 매이지 않아 **글을 지워도 파일이 남았다.** 교환일기 사진이 그렇다는 건
지운 뒤에도 주소만 알면 볼 수 있다는 뜻이다.

사진·앨범은 **파일 먼저, 행 나중**이고 여기는 **행 먼저, 파일 나중**이다.
같은 사진이 다른 글에도 붙어 있을 수 있어서다(마크다운을 복사해 옮기면 그렇게 된다).
행을 먼저 지우면 "아직 쓰이는가" 가 그냥 "DB 어디든 이 주소가 있나" 가 되어 단순해진다.
여덟 군데를 세어 0 일 때만 지우고, 확인에 실패하면 지우지 않는다 — 쓰이는 사진을
지우는 것보다 고아로 남기는 게 낫다. 글 지우는 일을 파일 정리 실패로 막을 이유도 없다.

**배포에서 실측**(2026-09-20): 아기 기록에 사진을 넣어 저장 → `HEAD` 200 · 94바이트,
기록 삭제 → 약 8초 뒤 **404**. blob 삭제는 바로가 아니라 몇 초 걸린다 —
2초 만에 확인하면 아직 200 이 나온다(앞서 "안 지워졌나" 했던 것도 이 지연이었을 것).


### 지우기 전에 묻는 기준 — "다시 만들 수 있는가"

확인이 제각각이었다: 앨범·사진은 모달, 아기 기록·계획은 브라우저 `confirm`,
게시글·대화·할일·장보기·기념일·캘린더는 **아무것도 없음**.

모든 삭제에 확인을 붙이는 건 답이 아니다. 장보기 항목은 3초면 다시 담으니
묻는 쪽이 느리다. **잃는 것에 비례해서** 묻는다:

| 잃는 것 | 다시 만들기 | 묻나 |
|---|---|---|
| 장보기·할일·기념일·일정 | 몇 초 | 안 묻는다 |
| 가족이 쓴 글·아기 기록·포동이 대화·사진·앨범·계획 | **불가** | 묻는다 |

`useConfirm()` 하나로 모았다(`components/ui/confirm-dialog.tsx`).
`window.confirm` 은 쓰지 않는다 — 사이트의 말투도 모양도 따르지 않고,
무엇이 사라지는지 적을 자리도 없다.


### 손가락이 닿는 넓이 — 규칙만 적어 두고 재 본 적이 없었다

DESIGN.md 는 "모바일 탭 타깃 ≥ 40px" 이라고 적어 뒀는데 한 번도 재지 않았다.
재 보니 **장보기 체크 동그라미가 24px**, 계획 준비물 20px, `…` 32px,
추천 칩은 26px 짜리가 스물일곱 개 붙어 있었다. 마트에서 카트를 밀며 누르는 게 24px 이다.

- **작아야 예쁜 것**(체크 동그라미)은 `.tap-target` 으로 보이지 않는 넓이만 44px 로.
  폰에서만 적용한다 — 데스크톱에서 나란한 아이콘끼리 겹치면 엉뚱한 게 눌린다.
- **그 밖의 버튼·칩**은 실제 크기를 키운다(`h-10 lg:h-8`). 목록에서 가짜 영역을 쓰면
  옆 글자를 덮어 이름을 누르려다 지워질 수 있다.
- 글자 링크는 `-my-3 py-3` 처럼 자리를 뺏지 않고 높이만.

**검사식이 세 번 틀렸고 변이 테스트가 세 번 다 잡았다.**
① 중심에서 잰 거리에 폭을 또 더해 두 배로 셌다(24px 이 46px 로 나와 다 통과했다).
② 첫 화면만 쟀다(스크롤 아래를 놓쳤다).
③ 화면 가장자리 막대에 가려진 채로 쟀다(실제보다 작게 나왔다).
**"검사가 통과했다" 는 검사가 맞을 때만 뜻이 있다.**


### 믿을 수 없는 검사는 남기지 않는다

글자 대비도 "확보한다" 고만 적어 두고 재 본 적이 없었다. 재 보니 흐린 회색이
**2.41:1** — 날짜·개수·수량이 사실상 안 읽혔다. 세 단계를 다시 잡되 간격도 같이 봤다
(대비만 맞추면 한 덩어리가 되어 위계가 사라진다).

실제로 **그려진 글자**를 재는 측정기도 만들어 봤다. 그런데 그라데이션 배경, 알파 합성,
이모지를 다 다뤄야 했고 — 이모지를 글자색으로 재고 있었다. 101건이 나왔는데 대부분 거짓이었다.
**그래서 그건 버리고 토큰 값을 보는 단위 테스트만 남겼다.** 단색 배경 위의 글자는
정확히 계산되고 결과가 흔들리지 않는다. 그 자리가 `ink` 세 단계가 실제로 놓이는 곳이다.

탭 타깃 때 검사식이 세 번 틀렸던 것과 같은 교훈이다 —
**"검사가 통과했다" 는 검사가 맞을 때만 뜻이 있다.**


### 검사가 여섯 가지를 본다

`npm run ui:audit -- <주소> <아이디> <비밀번호>` — 폰·태블릿·데스크톱 세 폭.

| | 무엇을 |
|---|---|
| 가로 스크롤 | body 가 옆으로 밀리는가 |
| 가려짐 | 떠 있는 것이 글자·버튼을 덮는가(가장자리 막대는 예외) |
| `…` 메뉴 | 펼친 항목이 잘리는가, 바깥을 누르면 닫히는가 |
| 탭 타깃 | 폰에서 **눌리는 넓이**가 40px 이상인가, 서로 훔치지 않는가 |
| 키보드 | 포커스 표시가 보이는가, 떠 있는 판이 탭을 가두는가 |
| 글자 확대 | 글자 크기 1.5배에서 글이 반 넘게 잘리지 않는가 |
| 페이지 길이 | 몇 화면어치인가 |

`npm run ui:flows` 는 **눌러 본다**(29단계, 로컬 전용).
`npm test` 안에 색 대비(토큰 값)와 날짜·주차 계산이 들어 있다.


### 실패는 조용히 지나가면 안 된다

DESIGN.md 는 "오류는 방법을 알려준다" 고 적어 뒀는데 코드는 **모든 실패를 말없이
되돌리고** 있었다. 담은 게 사라지고, 지운 게 되살아나고, 설명이 없었다.

특히 **네트워크가 끊기면 `fetch` 는 거부된다** — `if (!res.ok)` 만으로는 안 잡힌다.
와이파이가 끊긴 상황이 정확히 이 경우인데, 그때 예외가 조용히 사라져
"눌렀는데 아무 일도 없다" 가 됐다. 저장하는 자리마다 `catch` 가 필요하다.


### 검사가 안 보던 자리

모든 검사가 **로그인부터 하고 시작**했다. 그래서 가족이 제일 먼저 보는 화면이
스물두 조각이 지나도록 한 번도 안 재졌다. 재 보니 화면 자체는 멀쩡했지만
오류 안내 글자가 2.84:1 이었고, 거기서 실마리를 잡아 보니 `text-danger` 를 쓰는
**모든 자리**가 기준 미달이었다(확인 대화의 "지우기" 버튼 포함).

검사를 만들 때는 **그 검사가 무엇을 안 보는지**도 같이 적어 둘 것.


### 내가 빼 둔 것과, 고치고 안 고친 글

`/admin` 을 "관리자 전용" 이라며 **내가 개편 대상에서 뺐다.** 사용자가 그러라고 한 적은
없다. 그 사이 폰에서 4.0화면짜리로 남아 있었고 — 형님이 쓰는 화면이다.
지금은 1.5화면. `ui:audit` 에도 넣었다.

그리고 거기 적힌 **꾸미기 안내가 없어진 버튼을 가리키고 있었다**("우하단 꾸미기 버튼").
12번째 조각에서 상단바로 옮겨 놓고 그 화면을 **설명하는 글**은 안 고쳤다.
**화면을 고치면 그 화면을 설명하는 글도 같이 본다.**


### 잘못됐을 때 무엇이 보이는가

무료 티어 데이터베이스는 잠들었다 못 깨는 일이 있다. 그때 가족이 보던 것:
`"This page couldn't load. A server error occurred. ERROR 2859280536"` —
영어인 데다 **셸이 통째로 사라져** 다른 곳으로 갈 수도 없었다.
`loading.tsx` 는 있는데 `error.tsx` 가 없었다.

지금은 한국어로 말하고 탭바가 남는다. **"다시 불러오기" 가 진짜로 복구하는지도
확인했다** — 첫 요청만 실패시켜 두고 눌렀더니 목록이 돌아왔다.
안 되는 버튼은 없느니만 못하다.


### dev 에서 본 것을 그대로 믿으면 안 된다

느린 연결에서 탭을 누르면 1.2초 동안 아무 일도 안 일어나 보였다. 경로마다
`loading.tsx` 를 깔았는데 — **프로덕션 빌드로 재 보니 원래도 잘 되고 있었다.**
탭은 150ms 안에 켜지고 주소도 바로 바뀐다. `next dev` 가 프리페치를 하지 않아
멈춘 것처럼 보였을 뿐이다. 11개 파일은 지웠다.

화면이 느린지 빠른지는 **프로덕션 빌드로** 잰다:
`npm run build && PORT=3100 npm start`.

남긴 것은 모양과 말뿐이다 — 도는 표시 대신 올 내용의 뼈대, 그리고
사이트 안에서 옮겨 다니는데 "포동을 여는 중" 이라고 하지 않기.


### 배포본에 함부로 올리지 않는다 — 내가 낸 사고

아기 페이지에 **파란 얼룩 두 개**가 떠 있었다. 사용자가 발견해서 알려 줬다.
내가 프로덕션에서 "기록에 사진 붙이기" 를 시험하다가 `input[type="file"]` 을
`.first()` 로 짚었는데, 그게 글쓰기 칸이 아니라 **꾸미기 스티커 업로드 칸**이었다.
8×8 짜리 테스트 이미지가 150px 로 늘어나 아기 일기 위에 두 장 붙었다.

지웠다(94바이트짜리만 골라서 — 형님이 홈에 붙인 2.2MB 스티커는 그대로).

**규칙**: 올리고 지우는 시험은 로컬에서만 한다(`ui:flows` 는 이미 거부한다).
배포본에서는 **읽기만** 한다. 부득이 올려야 하면 파일 선택칸을 그 모달 안으로
좁혀서 짚는다(`.fixed.inset-0.z-50 input[type="file"]`).

### 남은 것

- **배포 Blob 에 오늘 이전 고아 파일이 있을 수 있다.** 세려면 토큰이 필요하니 물어볼 것.
- **포동이가 기념일·장보기를 실제로 만드는지** 확인 안 됨(실제 모델 호출이 드니 물어볼 것).
  확인되면 빈 화면에서 "포동이에게 부탁하기" 를 권할 수 있다.

27조각을 하고 배포본을 본 사용자의 말: **"뭔가 vercel에 배포된걸로 보면 혁신적으로
바뀐건 없네?"** 맞는 말이었다. 1회차에서 나는 *"다시 칠하지 않는다. 구조만 고친다"* 고
스스로 정했고, 그대로 27번을 구조만 고쳤다. 고친 것들은 진짜였지만(시간대·가려짐·
안 지워지던 파일·탭 타깃) **보이지 않는 것들**이었다.

물었더니 답은 **"확 바꿔줘 — 새 느낌으로"**.

### 컨셉: 「편지」

두 사람이 셋이 되기를 기다리는 집. 이 사이트엔 아기에게 쓰는 **편지**가 있다.
- **틀은 진하게, 내용은 밝게.** 사이드바·상단바·탭바·히어로가 진한 자두 먹(`#362c4e`),
  그 안은 옅은 라일락 종이(`#eceaf2`) 위 흰 판.
- **제목은 한글 명조**(고운바탕), 본문은 Pretendard. Fredoka 는 뺐다.
- **과감함은 한 곳에** — 주차 숫자. `8주 1일` 이 화면에서 가장 크다.

### 왜 진한 바탕 전체가 아니라 '진한 틀' 인가

고른 안에는 `진한 배경` 이라고 적혀 있었는데 내용판은 밝게 두었다. 이유 둘:

1. **스티커.** 가족이 올린 꾸미기 스티커는 배경이 비치는 PNG 이고 밝은 바탕에 맞춰
   골라 붙인 것이다. 판을 어둡게 하면 테두리가 허옇게 뜨거나 아예 안 보인다.
   가족이 직접 만든 것을 개편이 망가뜨리면 안 된다.
2. **사진.** 앨범·아기 기록의 사진이 이 판 위에 산다. 진한 틀이 사진을 둘러싸면
   사진이 더 또렷해지고, 판이 밝으니 스티커도 그대로 산다.

모서리는 그대로 둥글게 뒀다(`각진 편집 레이아웃` 대신). 「포동」이라는 이름 자체가
둥근 말이다. 다만 **한 값으로 전부 둥글리던 것**은 그만뒀다 — 칩·판·사진·히어로가
각기 다른 모서리를 갖고, 크기가 아니라 무엇인가로 고른다.

### 함께 고친 진짜 버그

- **홈 히어로의 사진 자리**가 `absolute -right-4 -top-4` 였다. 사진을 넣어 두면
  390px 에서 인사말 둘째 줄 위로 올라온다. 이제 나란히 놓는다 — 겹칠 자리가 없다.
  (⚠️ 아래 "진단이 또 틀렸다" 참고 — 배포본 사진에서 인사말을 덮고 있던 것은
  이 자리가 아니라 **가족이 붙인 꾸미기 스티커**였다.)
- **아기 페이지 맨 위에 `기록 남기기` 버튼만 떠 있었다.** 폰에서는 제목이 상단바로
  올라가 그 줄에 버튼 하나만 남는다. 무엇에 더하는 버튼인지 알 수 없었다.
  더해지는 목록(`일기`) 옆으로 내렸다.
- **주요 버튼의 흰 글자가 AA 를 못 넘고 있었다**(4.01:1). 검사에 넣고 색을 한 단 낮췄다.

### 진단이 또 틀렸다 — 인사말을 덮고 있던 건 히어로 사진이 아니었다

28조각을 배포하고 폰 사진을 다시 봤더니, 인사말 오른쪽을 덮은 **사진이 그대로 있었다.**
히어로를 고쳤는데 왜 그대로인가 — 확인해 보니 `heroImageUrl` 은 애초에 `null` 이었다.

덮고 있던 것은 **가족이 홈에 붙여 둔 꾸미기 스티커**다.
`/api/decorations?page=/` → `xPct 92.6% · width 150px`.
데스크톱(내용 폭 ~1160px)에서는 999~1149px 로 딱 안쪽에 들어오지만,
폰(358px)에서는 286~436px 이라 **46px 이 화면 밖으로 나간다**. 같은 값이 화면 폭에
따라 다른 자리를 뜻한다. 가족은 넓은 화면에서 오른쪽 끝에 붙였을 뿐이다.

고친 방법: **저장값은 건드리지 않고 그리는 자리만 가둔다.**
`left: clamp(width/2, xPct%, 100% - width/2)` — 넓은 화면에서는 붙인 그대로,
좁은 화면에서만 안쪽으로 들어온다. 편집 중에는 가두지 않는다(끌고 있는 손가락과
그림이 어긋나면 안 된다).

**두 번째 교훈이 같은 모양이다.** 26조각에서도 "느린 페이지 전환" 을 dev 에서 보고
잘못 진단했다. 이번엔 화면에 보이는 사진을 코드에서 찾은 사진과 **같은 것이라고
가정**했다. 화면에 있는 것이 무엇인지는 화면에 물어봐야 한다 — `/api/site-config` 를
한 번 부르면 30초면 끝날 일이었다.


### 개편 2·3 에서 배운 것

**빈 화면을 다듬지 않는다.** 배포본에서 앨범·할일·기념일·게시판은 여전히 0이다.
그래서 예쁜 순서가 아니라 **여는 순서**로 고쳤다 — 계획 상세(발리 준비물)가 먼저였다.

**같은 크기로 외치는 것이 셋이면 강조가 없는 것과 같다.** 기념일이 D-day 셋을
48px 로 나란히 외치고 있었다. 아기 페이지의 주차 숫자와 같은 목소리다.
가장 가까운 하나만 크게 두고 나머지를 줄로 내리니 여섯이 한 화면에 들어왔다.

**폰에서 제목이 상단바로 올라가면 그 줄에 버튼만 남는다.** 넷이 그랬다.
제목을 다시 쓰면 같은 말을 두 번 하게 되니 **셈**을 놓았다(`PageHeader summary`).
"계획 2개" 는 제목의 되풀이가 아니라 새 정보다.

**`flex gap` 은 글자 사이도 벌린다.** `<p className="flex gap-1.5">일정 <span>5</span>개</p>`
가 "일정 5 개" 로 보였다. flex 안에서는 텍스트 조각 하나하나가 항목이다.
한 덩어리로 감싸면 된다. 전 파일을 훑어 같은 모양을 찾았다(하나뿐이었다).

**검사가 스스로를 망가뜨리고 있었다.** ui-flows 의 한 단계가 실패하면 그 흐름이 만든
것이 남고, 다음 판에서 "지웠는데 서버엔 남아 있다" 로 **엉뚱하게** 실패했다.
시작할 때 MARK 가 붙은 것을 걷어내게 했다 — 몇 번을 돌려도 같은 결과가 나온다.
검사는 자기가 만든 것을 실패해도 치워야 한다.


### 개편 4·5 에서 배운 것

**가장 많이 쓰는 것을 마지막에 손대고 있었다.** 배포본 대화가 열 개다. 할일 0, 앨범 0,
기념일 0인 사이트에서 제일 많이 쓰는 기능인데 개편 네 번 동안 한 번도 열어 보지 않았다.
"화면 목록" 을 순서대로 훑으면 이렇게 된다 — **쓰는 순서로 훑어야 한다.**

**체크는 동그라미가 아니라 줄 전체로.** 장보기는 마트에 서서 한 손으로 쓰는 화면인데
눌리는 자리가 24px 동그라미뿐이었다. 버튼 안에 버튼을 넣을 수 없어서
`CheckCircle`(모양만)과 `Checkbox`(동그라미가 그대로 버튼)를 갈랐다.

**색만으로는 아무것도 전할 수 없다.** 장보기의 분류 색 점은 체크 동그라미와 같은 색을
두 번 말하고 있었고, 분류 **이름은 어디에도 없었다**. 색을 봐도 무슨 분류인지 알 수 없는
색은 정보가 아니라 얼룩이다. 뺐다.

**이름을 자세히 적으면 선택자가 흔들린다.** 휴지통을 `"우유 지우기"` 로 바꾸자
확인 대화상자의 `지우기` 와 겹쳐 검사가 깨졌다. 접근성을 위한 이름은 옳고,
검사를 `exact` 로 좁히는 쪽이 맞다.

### 하마터면 — 배포본에서 "첫 번째 버튼" 을 눌렀다

지난 대화 목록에서 `.first()` 버튼을 누르는 스크립트를 **배포본에** 돌렸다.
목록에는 휴지통이 섞여 있다. 마침 DOM 순서가 제목이 먼저라 대화가 열렸을 뿐,
반대였으면 가족의 대화 하나가 사라졌다. 열 개 그대로인 것을 확인하고 스크립트를 고쳤다.

앞선 사고(시험용 사진을 배포본에 올린 일)와 **같은 모양**이다: 선택자를 느슨하게 쓰면
무엇을 누를지 모르는 채로 누르게 된다. "배포본에서는 읽기만 한다" 는 규칙은
**무엇을 누를지 정확히 알 때만** 지켜진다. 배포본에서 누르는 것은 이름으로 짚는다.
