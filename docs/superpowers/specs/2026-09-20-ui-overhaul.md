## 네 개의 렌즈 — 같은 화면을 다르게 본다

문제 13개는 목록일 뿐이다. 무엇을 먼저 고칠지는 렌즈가 정한다.

**① 쓰는 순간.** 마트에서 카트를 밀며 한 손으로 장보기. 병원 대기실에서 아기 기록.
소파에서 저녁에 사진과 게시판. 책상에서 주말에 계획과 앨범 정리.
→ 폰에서 하는 일은 대부분 **보기와 체크**고, 긴 입력은 책상에서 한다.
그런데 지금은 폰에서도 모든 페이지가 **입력 폼을 먼저** 보여준다(문제 12). 거꾸로다.

**② 엄지.** 390×844 폰에서 한 손 엄지가 편히 닿는 곳은 화면 아래 3분의 1이다.
지금 네비게이션도 위(햄버거), 주요 액션(`+ 추가`)도 위, 페이지 제목도 위에 있다.
아래쪽 3분의 1은 FAB 두 개가 콘텐츠를 가리는 데만 쓰인다(문제 1·2).

**③ 누가.** 관리자는 한 명이고 나머지 가족은 읽고 쓰기만 한다.
`꾸미기` FAB 은 이미 **관리자에게만** 뜬다(`app-shell.tsx`) — 대부분의 가족에게 FAB 은 `물어보기` 하나다.
그러니 가리는 문제를 풀려고 `물어보기`를 건드릴 필요가 없다. **`꾸미기`를 FAB 층에서 빼면 된다.**

**④ 얼마나 자주.** 매일 = 홈·할일·장보기. 주 단위 = 캘린더·아기·게시판.
가끔 = 사진첩·기념일·계획. 드물게 = 관리자.
→ 탭 순서와 홈 카드 순서의 근거. 빈도가 낮다고 없애는 게 아니라, **한 단계 안으로** 넣는다.

## 방향

### 아래쪽 가장자리를 한 곳에서 정한다

폰 하단은 탭바·`물어보기` FAB·콘텐츠 여백·iOS 안전영역이 서로 밀어내는 자리다.
페이지마다 따로 맞추면 또 가린다. `components/app-shell.tsx` 가 CSS 변수 하나로 정하고,
FAB 과 `main` 의 아래 여백이 **그 값을 읽는다**.

```
--bottom-bar : 탭바 높이 + env(safe-area-inset-bottom)   (lg 에서는 0)
물어보기 FAB : bottom = var(--bottom-bar) + 12px
main 아래 여백: var(--bottom-bar) + FAB 높이 + 여유
```

### 바꾸는 것

1. **폰 하단 탭바.** `getNav()` 의 **앞 4개 + 더보기**. 두 번째 목록을 만들지 않는다 —
   `NavItem` DB 오버라이드와 꾸미기 표면이 모두 NAV href 를 기준으로 돌기 때문이다.
   순서는 `lib/nav.ts` 한 줄이라 언제든 바꿀 수 있다. 렌즈 ④로 정한 앞 4개:
   **홈 · 할일 · 장보기 · 사진첩**. `더보기`는 **지금 있는 드로어**를 연다(나머지 5개 + 관리자 + 로그아웃).
2. **`꾸미기`를 FAB 층에서 뺀다.** 관리자 전용·가끔 쓰는 기능이라 페이지 헤더 안으로.
   계획 히어로의 ✨ 버튼(embedded 표면)은 그대로 둔다.
3. **폰 상단바가 현재 페이지를 말한다.** 모든 페이지에서 "포동 / 우리 가족 공간"을 반복하는 대신
   그 페이지의 이모지+제목을. `PageHeader` 의 설명은 `hidden lg:block`. 문제 5의 대부분이 여기서 준다.
4. **빈 것은 자리를 덜 차지한다.** 홈에서 비어 있는 카드는 한 줄로 접고 추가 버튼만 남긴다.
5. **기념일은 목록 하나.** 위 3건을 크게, 나머지는 이어서. 같은 항목을 두 번 싣지 않는다.
6. **항목 액션을 모은다.** 폰에서 항목당 아이콘 2~4개 대신 `…` 하나.
   AGENTS.md 의 "hover 로만 뜨는 액션 금지"는 지킨다 — 숨기는 게 아니라 **합치는** 것이다.
7. **목록이 먼저, 입력은 아래.** 게시판·장보기의 폼은 접거나 하단 고정 한 줄로.
8. **폰 달력은 격자 대신 일정 목록**(주 단위)으로. 격자는 lg 에서.
9. 계획 히어로 세로 정렬(문제 10) · 드로어 Escape(8) · 데스크톱 사진 줄 잘림(9) · 아기 날짜 입력(13).

### 바꾸지 않는 것

팔레트·타이포·모서리·그림자 토큰, 6색 분류, 냉장고 문 컨셉, URL, 데이터 패턴.
`/admin`(관리자 전용, 4.1화면)은 이번 개편 대상이 아니다.

### 순서 — 한 조각씩, 각각 커밋·테스트·양쪽 폭 확인

`ui-before-redesign` 태그가 바닥이고, 조각마다의 커밋이 더 촘촘한 되돌림 지점이 된다.

1. 앱 셸 — 탭바 · 상단바 제목 · FAB 재배치 · 하단 여백 일원화 · Escape. (DESIGN.md·AGENTS.md 같이 갱신)
2. 홈 — 빈 섹션 접기 · 오늘 먼저 · 데스크톱 사진 줄.
3. 기념일 — 목록 하나 · 항목 액션 패턴을 여기서 만들어 나머지에 쓴다.
4. 장보기·할일 — 목록 먼저, 입력은 하단.
5. 게시판·계획 상세·아기·캘린더.

### 프로덕션에서만 보인 것 — 로컬 시드로는 안 나왔다

- 서버가 UTC 로 돌아 **한국시간 0시~9시 사이 "오늘 할일" 이 어제 것**을 보여 줬다.
  인사말도 오후 3시에 "늦은 밤이에요". `instrumentation.ts` 에서 시간대를 맞춘다.
  Vercel 런타임에서 인사말이 "나른한 오후네요" 로 바뀌는 것으로 확인.
- 꾸미기 스티커가 뷰포트 밖으로 나가 폰이 가로로 34px 밀렸다.
- 구성원이 없어 "가족 0명" 만 떠 있었다.

**다음에도 이 순서로.** 로컬 시드는 깨끗해서 아무것도 안 알려 준다.
배포본을 폰 폭으로 열고, 떠 있는 것을 눌러 보는 쪽이 목록에 남은 어떤 손질보다 낫다.

### 두 번 겪고 알게 된 것 — 떠서 겹치는 것은 제자리에 그리지 않는다

`…` 메뉴가 카드의 `overflow-hidden` 에 잘려 **아래 항목을 아예 누를 수 없던 일**이
계획 상세와 할일에서 잇따라 났다. 처음에는 그 카드의 overflow 를 옮겨 막았는데,
카드마다 손보는 식으로는 다음 자리에서 또 난다. 지금은 메뉴를 `document.body` 로
내보내고(portal) 버튼 위치를 재서 띄운다 — 조상의 overflow 도 게시판 쪽지의
transform 도 상관없다. **앞으로 메뉴·툴팁·팝오버는 portal 로.**

검사가 이걸 놓친 이유도 적어 둔다: 그때 `/todos` 에 오늘 할일이 하나도 없어
`…` 버튼 자체가 없었다. **빈 화면은 아무것도 증명하지 못한다.**

### 실제로 무엇을 쓰는지 세어 봤다 (2026-09-20, 배포본)

| 곳 | 개수 |
|---|---|
| 포동이와의 대화 | **9** |
| 아기 기록 | 있음(교환일기·검진) |
| 계획 | 1 (발리, 준비물 51개) |
| 일정 | 1 |
| 앨범 · 할일 · 장보기 · 기념일 · 게시판 | **전부 0** |

내가 정한 탭은 홈 · 할일 · 장보기 · 사진첩이었다 — **넷 중 셋이 빈 곳**이었다.
"가족 사이트라면 대개 이렇겠지" 하고 정한 것이지 이 가족을 보고 정한 게 아니었다.
지금은 홈 · 아기 · 장보기 · 계획. 장보기만 0인데도 남겼다 — 데이터가 시킨 게 아니라
지난 조각에서 한 화면에 들어오게 고쳤으니 이제는 쓸 만하리라는 **기대**다. 아니면 빼면 된다.

**가장 많이 쓰는 건 포동이다.** 대화 아홉 번 대 할일 0. 화면에서는 우하단의
작은 흰 알약 하나뿐이다.


### 세 번째로 배운 것 — 보는 것과 쓰는 것은 다르다

아기 페이지를 여러 번 **봤지만** 한 번도 **쓰지** 않았다. 기록을 남겨 보니 저장은 되는데
고치기가 안 됐다. 기록의 `…`(x 321–353, y 723–755)와 우하단 `물어보기` FAB(x 261–374,
y 726–776)이 겹쳐 있었고, 그 한가운데의 최상위 요소는 FAB 이었다 —
**일기를 고치려고 누르면 AI 채팅이 열렸다.**

내가 검사에서 "스크롤 도중 가려지는 건 정상" 이라 넘긴 것이 원인이다. 글자에는 맞는
말이지만 버튼에는 아니다: 글은 스쳐 지나가면 그만이고 버튼은 그 자리에서 누르면
**다른 것이 눌린다.** 검사를 고치니 사이트 전체에서 9건이 나왔다.

이제 떠 있는 것은 하단 탭바뿐이다(화면 가장자리, 모든 모바일 앱의 약속).
`포동이` 는 탭바 안·사이드바 위로 들어갔다. AGENTS.md 에 규칙으로 적었다.


### 화면은 보는 것으로 끝나지 않는다 — 검사가 두 벌인 이유

`npm run ui:audit` 은 **보이는 것**을 잰다(가로 스크롤·가려짐·메뉴 잘림).
`npm run ui:flows` 는 **눌러 본다**(만들고·고치고·지우고, 새로고침 뒤에도 그대로인지).
후자가 없으면 못 찾는 것들:

| 무엇 | 어떻게 드러났나 |
|---|---|
| 일기를 고치려면 AI 채팅이 열렸다 | `…` 가 떠 있던 버튼에 덮여 있었다 |
| 아래로 내려간 채 `…` 를 누르면 아무 일도 안 일어났다 | 메뉴가 열리자마자 스크롤에 스스로 닫혔다 |
| 이름 없는 체크박스 세 곳 | 스크린리더에 "체크박스" 라고만 |

`ui:flows` 는 로컬이 아니면 스스로 거부한다 — 실제로 만들고 지우기 때문이다.


올린 파일이 남는 갈래는 이제 다 막혔다: **사진·앨범·글 속 사진·스티커** 넷.

### "삭제" 라고 했으면 지워져야 한다

사진을 지우면 DB 행만 사라지고 **파일은 남아 있었다.** 배포에서는
무료 용량(Vercel Blob)을 계속 먹고, 주소를 아는 사람은 "지운" 가족 사진을 그대로 본다.

지금은 **파일을 먼저 지우고 행을 지운다.** 순서가 중요하다 — 행을 먼저 지우면
파일 삭제가 실패했을 때 어느 파일이었는지조차 모르는 고아가 남는다. 못 지우면
502 와 "사진 파일을 못 지웠어요" 를 돌려주고 행은 그대로 둔다.

**배포에서 실측했다**(2026-09-20): 사진을 올려 `HEAD` 200 · 94바이트를 확인하고,
앨범을 지운 뒤 2초 만에 **404**. blob 삭제 경로가 실제로 돈다.
(로컬 `unlink` 경로는 `ui:flows` 가 파일 개수로 매번 확인한다.)


### 글 안의 사진 — 방향이 반대인 이유

게시판·아기 기록·계획 설명에는 글 안에 사진을 넣을 수 있는데(MarkdownEditor),
앨범에 매이지 않아 **글을 지워도 파일이 남았다.** 교환일기 사진이 그렇다는 건
지운 뒤에도 주소만 알면 볼 수 있다는 뜻이다.

사진·앨범은 **파일 먼저, 행 나중**이고 여기는 **행 먼저, 파일 나중**이다.
같은 사진이 다른 글에도 붙어 있을 수 있어서다(마크다운을 복사해 옮기면 그렇게 된다).
행을 먼저 지우면 "아직 쓰이는가" 가 그냥 "DB 어디든 이 주소가 있나" 가 되어 단순해진다.
여덟 군데를 세어 0 일 때만 지우고, 확인에 실패하면 지우지 않는다 — 쓰이는 사진을
지우는 것보다 고아로 남기는 게 낫다. 글 지우는 일을 파일 정리 실패로 막을 이유도 없다.

**배포에서 실측**(2026-09-20): 아기 기록에 사진을 넣어 저장 → `HEAD` 200 · 94바이트,
기록 삭제 → 약 8초 뒤 **404**. blob 삭제는 바로가 아니라 몇 초 걸린다 —
2초 만에 확인하면 아직 200 이 나온다(앞서 "안 지워졌나" 했던 것도 이 지연이었을 것).


### 지우기 전에 묻는 기준 — "다시 만들 수 있는가"

확인이 제각각이었다: 앨범·사진은 모달, 아기 기록·계획은 브라우저 `confirm`,
게시글·대화·할일·장보기·기념일·캘린더는 **아무것도 없음**.

모든 삭제에 확인을 붙이는 건 답이 아니다. 장보기 항목은 3초면 다시 담으니
묻는 쪽이 느리다. **잃는 것에 비례해서** 묻는다:

| 잃는 것 | 다시 만들기 | 묻나 |
|---|---|---|
| 장보기·할일·기념일·일정 | 몇 초 | 안 묻는다 |
| 가족이 쓴 글·아기 기록·포동이 대화·사진·앨범·계획 | **불가** | 묻는다 |

`useConfirm()` 하나로 모았다(`components/ui/confirm-dialog.tsx`).
`window.confirm` 은 쓰지 않는다 — 사이트의 말투도 모양도 따르지 않고,
무엇이 사라지는지 적을 자리도 없다.


### 손가락이 닿는 넓이 — 규칙만 적어 두고 재 본 적이 없었다

DESIGN.md 는 "모바일 탭 타깃 ≥ 40px" 이라고 적어 뒀는데 한 번도 재지 않았다.
재 보니 **장보기 체크 동그라미가 24px**, 계획 준비물 20px, `…` 32px,
추천 칩은 26px 짜리가 스물일곱 개 붙어 있었다. 마트에서 카트를 밀며 누르는 게 24px 이다.

- **작아야 예쁜 것**(체크 동그라미)은 `.tap-target` 으로 보이지 않는 넓이만 44px 로.
  폰에서만 적용한다 — 데스크톱에서 나란한 아이콘끼리 겹치면 엉뚱한 게 눌린다.
- **그 밖의 버튼·칩**은 실제 크기를 키운다(`h-10 lg:h-8`). 목록에서 가짜 영역을 쓰면
  옆 글자를 덮어 이름을 누르려다 지워질 수 있다.
- 글자 링크는 `-my-3 py-3` 처럼 자리를 뺏지 않고 높이만.

**검사식이 세 번 틀렸고 변이 테스트가 세 번 다 잡았다.**
① 중심에서 잰 거리에 폭을 또 더해 두 배로 셌다(24px 이 46px 로 나와 다 통과했다).
② 첫 화면만 쟀다(스크롤 아래를 놓쳤다).
③ 화면 가장자리 막대에 가려진 채로 쟀다(실제보다 작게 나왔다).
**"검사가 통과했다" 는 검사가 맞을 때만 뜻이 있다.**


### 믿을 수 없는 검사는 남기지 않는다

글자 대비도 "확보한다" 고만 적어 두고 재 본 적이 없었다. 재 보니 흐린 회색이
**2.41:1** — 날짜·개수·수량이 사실상 안 읽혔다. 세 단계를 다시 잡되 간격도 같이 봤다
(대비만 맞추면 한 덩어리가 되어 위계가 사라진다).

실제로 **그려진 글자**를 재는 측정기도 만들어 봤다. 그런데 그라데이션 배경, 알파 합성,
이모지를 다 다뤄야 했고 — 이모지를 글자색으로 재고 있었다. 101건이 나왔는데 대부분 거짓이었다.
**그래서 그건 버리고 토큰 값을 보는 단위 테스트만 남겼다.** 단색 배경 위의 글자는
정확히 계산되고 결과가 흔들리지 않는다. 그 자리가 `ink` 세 단계가 실제로 놓이는 곳이다.

탭 타깃 때 검사식이 세 번 틀렸던 것과 같은 교훈이다 —
**"검사가 통과했다" 는 검사가 맞을 때만 뜻이 있다.**


### 검사가 여섯 가지를 본다

`npm run ui:audit -- <주소> <아이디> <비밀번호>` — 폰·태블릿·데스크톱 세 폭.

| | 무엇을 |
|---|---|
| 가로 스크롤 | body 가 옆으로 밀리는가 |
| 가려짐 | 떠 있는 것이 글자·버튼을 덮는가(가장자리 막대는 예외) |
| `…` 메뉴 | 펼친 항목이 잘리는가, 바깥을 누르면 닫히는가 |
| 탭 타깃 | 폰에서 **눌리는 넓이**가 40px 이상인가, 서로 훔치지 않는가 |
| 키보드 | 포커스 표시가 보이는가, 떠 있는 판이 탭을 가두는가 |
| 글자 확대 | 글자 크기 1.5배에서 글이 반 넘게 잘리지 않는가 |
| 페이지 길이 | 몇 화면어치인가 |

`npm run ui:flows` 는 **눌러 본다**(29단계, 로컬 전용).
`npm test` 안에 색 대비(토큰 값)와 날짜·주차 계산이 들어 있다.


### 실패는 조용히 지나가면 안 된다

DESIGN.md 는 "오류는 방법을 알려준다" 고 적어 뒀는데 코드는 **모든 실패를 말없이
되돌리고** 있었다. 담은 게 사라지고, 지운 게 되살아나고, 설명이 없었다.

특히 **네트워크가 끊기면 `fetch` 는 거부된다** — `if (!res.ok)` 만으로는 안 잡힌다.
와이파이가 끊긴 상황이 정확히 이 경우인데, 그때 예외가 조용히 사라져
"눌렀는데 아무 일도 없다" 가 됐다. 저장하는 자리마다 `catch` 가 필요하다.


### 검사가 안 보던 자리

모든 검사가 **로그인부터 하고 시작**했다. 그래서 가족이 제일 먼저 보는 화면이
스물두 조각이 지나도록 한 번도 안 재졌다. 재 보니 화면 자체는 멀쩡했지만
오류 안내 글자가 2.84:1 이었고, 거기서 실마리를 잡아 보니 `text-danger` 를 쓰는
**모든 자리**가 기준 미달이었다(확인 대화의 "지우기" 버튼 포함).

검사를 만들 때는 **그 검사가 무엇을 안 보는지**도 같이 적어 둘 것.


### 내가 빼 둔 것과, 고치고 안 고친 글

`/admin` 을 "관리자 전용" 이라며 **내가 개편 대상에서 뺐다.** 사용자가 그러라고 한 적은
없다. 그 사이 폰에서 4.0화면짜리로 남아 있었고 — 형님이 쓰는 화면이다.
지금은 1.5화면. `ui:audit` 에도 넣었다.

그리고 거기 적힌 **꾸미기 안내가 없어진 버튼을 가리키고 있었다**("우하단 꾸미기 버튼").
12번째 조각에서 상단바로 옮겨 놓고 그 화면을 **설명하는 글**은 안 고쳤다.
**화면을 고치면 그 화면을 설명하는 글도 같이 본다.**


### 잘못됐을 때 무엇이 보이는가

무료 티어 데이터베이스는 잠들었다 못 깨는 일이 있다. 그때 가족이 보던 것:
`"This page couldn't load. A server error occurred. ERROR 2859280536"` —
영어인 데다 **셸이 통째로 사라져** 다른 곳으로 갈 수도 없었다.
`loading.tsx` 는 있는데 `error.tsx` 가 없었다.

지금은 한국어로 말하고 탭바가 남는다. **"다시 불러오기" 가 진짜로 복구하는지도
확인했다** — 첫 요청만 실패시켜 두고 눌렀더니 목록이 돌아왔다.
안 되는 버튼은 없느니만 못하다.


### dev 에서 본 것을 그대로 믿으면 안 된다

느린 연결에서 탭을 누르면 1.2초 동안 아무 일도 안 일어나 보였다. 경로마다
`loading.tsx` 를 깔았는데 — **프로덕션 빌드로 재 보니 원래도 잘 되고 있었다.**
탭은 150ms 안에 켜지고 주소도 바로 바뀐다. `next dev` 가 프리페치를 하지 않아
멈춘 것처럼 보였을 뿐이다. 11개 파일은 지웠다.

화면이 느린지 빠른지는 **프로덕션 빌드로** 잰다:
`npm run build && PORT=3100 npm start`.

남긴 것은 모양과 말뿐이다 — 도는 표시 대신 올 내용의 뼈대, 그리고
사이트 안에서 옮겨 다니는데 "포동을 여는 중" 이라고 하지 않기.


### 배포본에 함부로 올리지 않는다 — 내가 낸 사고

아기 페이지에 **파란 얼룩 두 개**가 떠 있었다. 사용자가 발견해서 알려 줬다.
내가 프로덕션에서 "기록에 사진 붙이기" 를 시험하다가 `input[type="file"]` 을
`.first()` 로 짚었는데, 그게 글쓰기 칸이 아니라 **꾸미기 스티커 업로드 칸**이었다.
8×8 짜리 테스트 이미지가 150px 로 늘어나 아기 일기 위에 두 장 붙었다.

지웠다(94바이트짜리만 골라서 — 형님이 홈에 붙인 2.2MB 스티커는 그대로).

**규칙**: 올리고 지우는 시험은 로컬에서만 한다(`ui:flows` 는 이미 거부한다).
배포본에서는 **읽기만** 한다. 부득이 올려야 하면 파일 선택칸을 그 모달 안으로
좁혀서 짚는다(`.fixed.inset-0.z-50 input[type="file"]`).

### 남은 것

- **배포 Blob 에 오늘 이전 고아 파일이 있을 수 있다.** 세려면 토큰이 필요하니 물어볼 것.
- **포동이가 기념일·장보기를 실제로 만드는지** 확인 안 됨(실제 모델 호출이 드니 물어볼 것).
  확인되면 빈 화면에서 "포동이에게 부탁하기" 를 권할 수 있다.

### 왜 진한 바탕 전체가 아니라 '진한 틀' 인가

고른 안에는 `진한 배경` 이라고 적혀 있었는데 내용판은 밝게 두었다. 이유 둘:

1. **스티커.** 가족이 올린 꾸미기 스티커는 배경이 비치는 PNG 이고 밝은 바탕에 맞춰
   골라 붙인 것이다. 판을 어둡게 하면 테두리가 허옇게 뜨거나 아예 안 보인다.
   가족이 직접 만든 것을 개편이 망가뜨리면 안 된다.
2. **사진.** 앨범·아기 기록의 사진이 이 판 위에 산다. 진한 틀이 사진을 둘러싸면
   사진이 더 또렷해지고, 판이 밝으니 스티커도 그대로 산다.

모서리는 그대로 둥글게 뒀다(`각진 편집 레이아웃` 대신). 「포동」이라는 이름 자체가
둥근 말이다. 다만 **한 값으로 전부 둥글리던 것**은 그만뒀다 — 칩·판·사진·히어로가
각기 다른 모서리를 갖고, 크기가 아니라 무엇인가로 고른다.

### 진단이 또 틀렸다 — 인사말을 덮고 있던 건 히어로 사진이 아니었다

28조각을 배포하고 폰 사진을 다시 봤더니, 인사말 오른쪽을 덮은 **사진이 그대로 있었다.**
히어로를 고쳤는데 왜 그대로인가 — 확인해 보니 `heroImageUrl` 은 애초에 `null` 이었다.

덮고 있던 것은 **가족이 홈에 붙여 둔 꾸미기 스티커**다.
`/api/decorations?page=/` → `xPct 92.6% · width 150px`.
데스크톱(내용 폭 ~1160px)에서는 999~1149px 로 딱 안쪽에 들어오지만,
폰(358px)에서는 286~436px 이라 **46px 이 화면 밖으로 나간다**. 같은 값이 화면 폭에
따라 다른 자리를 뜻한다. 가족은 넓은 화면에서 오른쪽 끝에 붙였을 뿐이다.

고친 방법: **저장값은 건드리지 않고 그리는 자리만 가둔다.**
`left: clamp(width/2, xPct%, 100% - width/2)` — 넓은 화면에서는 붙인 그대로,
좁은 화면에서만 안쪽으로 들어온다. 편집 중에는 가두지 않는다(끌고 있는 손가락과
그림이 어긋나면 안 된다).

**두 번째 교훈이 같은 모양이다.** 26조각에서도 "느린 페이지 전환" 을 dev 에서 보고
잘못 진단했다. 이번엔 화면에 보이는 사진을 코드에서 찾은 사진과 **같은 것이라고
가정**했다. 화면에 있는 것이 무엇인지는 화면에 물어봐야 한다 — `/api/site-config` 를
한 번 부르면 30초면 끝날 일이었다.


### 개편 2·3 에서 배운 것

**빈 화면을 다듬지 않는다.** 배포본에서 앨범·할일·기념일·게시판은 여전히 0이다.
그래서 예쁜 순서가 아니라 **여는 순서**로 고쳤다 — 계획 상세(발리 준비물)가 먼저였다.

**같은 크기로 외치는 것이 셋이면 강조가 없는 것과 같다.** 기념일이 D-day 셋을
48px 로 나란히 외치고 있었다. 아기 페이지의 주차 숫자와 같은 목소리다.
가장 가까운 하나만 크게 두고 나머지를 줄로 내리니 여섯이 한 화면에 들어왔다.

**폰에서 제목이 상단바로 올라가면 그 줄에 버튼만 남는다.** 넷이 그랬다.
제목을 다시 쓰면 같은 말을 두 번 하게 되니 **셈**을 놓았다(`PageHeader summary`).
"계획 2개" 는 제목의 되풀이가 아니라 새 정보다.

**`flex gap` 은 글자 사이도 벌린다.** `<p className="flex gap-1.5">일정 <span>5</span>개</p>`
가 "일정 5 개" 로 보였다. flex 안에서는 텍스트 조각 하나하나가 항목이다.
한 덩어리로 감싸면 된다. 전 파일을 훑어 같은 모양을 찾았다(하나뿐이었다).

**검사가 스스로를 망가뜨리고 있었다.** ui-flows 의 한 단계가 실패하면 그 흐름이 만든
것이 남고, 다음 판에서 "지웠는데 서버엔 남아 있다" 로 **엉뚱하게** 실패했다.
시작할 때 MARK 가 붙은 것을 걷어내게 했다 — 몇 번을 돌려도 같은 결과가 나온다.
검사는 자기가 만든 것을 실패해도 치워야 한다.


### 개편 4·5 에서 배운 것

**가장 많이 쓰는 것을 마지막에 손대고 있었다.** 배포본 대화가 열 개다. 할일 0, 앨범 0,
기념일 0인 사이트에서 제일 많이 쓰는 기능인데 개편 네 번 동안 한 번도 열어 보지 않았다.
"화면 목록" 을 순서대로 훑으면 이렇게 된다 — **쓰는 순서로 훑어야 한다.**

**체크는 동그라미가 아니라 줄 전체로.** 장보기는 마트에 서서 한 손으로 쓰는 화면인데
눌리는 자리가 24px 동그라미뿐이었다. 버튼 안에 버튼을 넣을 수 없어서
`CheckCircle`(모양만)과 `Checkbox`(동그라미가 그대로 버튼)를 갈랐다.

**색만으로는 아무것도 전할 수 없다.** 장보기의 분류 색 점은 체크 동그라미와 같은 색을
두 번 말하고 있었고, 분류 **이름은 어디에도 없었다**. 색을 봐도 무슨 분류인지 알 수 없는
색은 정보가 아니라 얼룩이다. 뺐다.

**이름을 자세히 적으면 선택자가 흔들린다.** 휴지통을 `"우유 지우기"` 로 바꾸자
확인 대화상자의 `지우기` 와 겹쳐 검사가 깨졌다. 접근성을 위한 이름은 옳고,
검사를 `exact` 로 좁히는 쪽이 맞다.

### 하마터면 — 배포본에서 "첫 번째 버튼" 을 눌렀다

지난 대화 목록에서 `.first()` 버튼을 누르는 스크립트를 **배포본에** 돌렸다.
목록에는 휴지통이 섞여 있다. 마침 DOM 순서가 제목이 먼저라 대화가 열렸을 뿐,
반대였으면 가족의 대화 하나가 사라졌다. 열 개 그대로인 것을 확인하고 스크립트를 고쳤다.

앞선 사고(시험용 사진을 배포본에 올린 일)와 **같은 모양**이다: 선택자를 느슨하게 쓰면
무엇을 누를지 모르는 채로 누르게 된다. "배포본에서는 읽기만 한다" 는 규칙은
**무엇을 누를지 정확히 알 때만** 지켜진다. 배포본에서 누르는 것은 이름으로 짚는다.


### 개편 6·7 에서 배운 것

**비어 있는 것이 답이었다.** 배포본 `/baby` 에 기록이 한 편도 없다. 태명·예정일·참고
사이트까지 다 넣어 둔 페이지인데 일기만 비어 있었다. 모달을 열어 보니 이유가 보였다 —
"오늘 입덧이 심했다" 한 줄을 남기려면 날짜 → 누가 → 종류 → 컨디션(이모지 여덟)을
지나야 글 칸이 나왔고, 저장 버튼은 화면 밖이었다.

**쓰지 않는 기능을 보면 "관심이 없나 보다" 가 아니라 "무엇이 막고 있나" 를 먼저 묻는다.**
여기서는 기능이 아니라 순서가 막고 있었다. 글 칸을 맨 위로 올리고 나머지를 접었다.

**지킬 수 없는 약속은 UI 문제다.** 할일의 `알림 켜기` 는 "마감 전에 알려드릴게요" 라고
했지만 알림은 창이 열려 있는 동안만 온다. 폰에서는 거의 언제나 거짓이 된다.
기능을 지우지 않고 **데스크톱에서만 내놓고 말을 사실대로** 바꿨다.
"곧 지원돼요" 라고 적힌 눌리지 않는 버튼(캘린더의 구글 연동)도 같은 종류였다 — 뺐다.

**검사에 통째로 빠진 화면이 있었다.** ui-flows 가 일곱 화면을 도는데 **아기가 없었다** —
두 번째 탭이고 가장 사적인 글이 쌓이는 곳인데. 네 단계를 더했다(34단계).
그중 하나는 "쓰는 칸보다 위에 정할 것이 있으면 실패" 로, 이번에 고친 것을 잠근다.


### 검사를 세 번 고쳐서야 잡은 것 — 라벨이 어디에도 안 붙어 있었다

로그인에서 라벨과 자리표시가 "아이디" 를 두 번 말하기에 자리표시를 지웠다.
그랬더니 `ui:audit` 이 칸을 못 찾았다. 원인은 자리표시가 아니라 **`Field`** 였다 —
라벨을 그리기만 하고 칸에 붙이지는 않고 있었다. 스크린리더가 읽던 이름은
자리표시였고, 자리표시는 **글자를 넣는 순간 사라진다.** 라벨을 눌러도 커서가
안 가던 것도 같은 이유다. `useId` 로 이어 붙이니 사이트의 모든 폼이 한 번에 고쳐졌다.

검사를 만드는 데 세 번이 걸렸고, 그 과정이 이 문서에서 제일 쓸모 있는 부분이다.

1. **목록 화면만 훑었다.** 12건을 찾았으니 쓸모가 있어 보였다. 그런데
   연결을 도로 끊어 보니 **0건**이었다 — 폼은 대개 모달 안에 있고, 안 열어 보면 안 보인다.
   *찾은 게 있다고 해서 찾아야 할 걸 찾는 검사는 아니다.*
2. **모달을 열어 보게 했더니** 이번엔 로그인이 `getByRole("textbox", {name:"아이디"})`
   로 칸을 찾다가 죽어서 **나머지 검사가 통째로 안 돌았다.** 재려는 그것이 깨지면
   눈이 같이 감기는 구조였다. 로그인은 이름이 아니라 구조(`autocomplete`)로 짚게 했다.
3. 이제 연결을 끊으면 **108건**이 나온다.

모달·작성칸을 열어 보게 하자 **한 번도 재지 않았던 자리**가 무더기로 드러났다:
마크다운 툴바 32×32, 색 고르개 32×32, 게시판 이모지 36×36, 이름 없는 입력칸 12곳.
접혀 있는 것은 없는 것과 같아서, 검사도 사람도 지나쳐 왔다.

**`.tap-target` 이 안 통하는 자리가 있다.** 게시판 작성자 아바타 넷은 6px 간격이라,
보이지 않게 44px 로 넓히면 서로 겹쳐 나중에 그려진 형제가 앞엣것을 덮는다 —
실제로 눌리는 폭은 32px 로 남았다. 붙어 있는 것들은 **보이는 크기 자체를** 키워야 한다.
검사가 "보임 32×32, 눌림 32×42" 로 그 차이를 그대로 보여 줬다.


### 기본값이 결정을 대신하고 있었다

배포본 홈에 아기가 안 보였다. 태명·예정일·참고 사이트까지 다 넣어 둔 가족인데.
`Baby.showOnHome` 의 기본값이 `false` 였다 — **끄기로 정한 게 아니라 그런 스위치가
있는 줄 몰랐던 것**이다(아기 설정 모달 안쪽에 있다).

값을 대신 바꾸지 않았다. 홈의 아기 카드 자리에 한 번 눌러 켜는 줄을 뒀다.
켜면 줄이 사라지고 카드가 선다. 설정은 여전히 가족의 것이다.

**기본값을 의심하는 습관을 여기 적어 둔다.** "안 쓰네" 로 보이는 것 중 상당수는
"그런 게 있는 줄 몰랐다" 이고, 그중 일부는 우리가 고른 기본값 탓이다.
아기 일기가 비어 있던 것도(개편 6), 홈에 아기가 없던 것도 같은 모양이었다.

### 고정 시간으로 재면 멀쩡한 것도 고장으로 잡힌다

"눌렀는데 그대로다" 로 두 번 실패했다. 기능은 멀쩡했고, 검사가 **1.5초만 기다렸다가**
확인한 것이 문제였다 — 서버 컴포넌트를 다시 받아 오는 시간은 그때그때 다르다.
`waitForTimeout` 대신 `waitFor({ state: "hidden" })` 로 **조건**을 기다리게 바꿨다.
검사에서 `waitForTimeout` 뒤에 곧바로 단정하는 자리는 전부 이 위험을 안고 있다.


### 내가 얹은 것이 내가 덜어낸 것보다 컸다

27조각에서 Pretendard 를 2.0MB → 157KB 로 줄여 놓고, 28조각에서 한글 명조를 얹으면서
**1,441KB 를 도로 얹었다.** 배포본 폰에서 홈 한 번에 3,649KB.

원인은 `next/font` 의 미리 받기(preload)다. 요청한 subset 의 파일을 전부
`<link rel=preload>` 로 거는데, 한글 글꼴은 구간이 100개쯤이라 첫 화면에서 통째로
받는다. `preload: false` 한 줄로 **94개 1,441KB → 6개 89KB.** 구간(unicode-range)은
그대로 남으므로 브라우저가 그 화면에 쓰인 글자가 든 구간만 받는다.

**새 것을 얹을 때는 전과 후의 무게를 잰다.** 안 재면 앞서 아낀 것을 모르는 새 되돌린다.

### 검사가 여러 회차 동안 거짓말하고 있었다 — 콘솔 오류 404

`ui-flows` 를 `npm start`(운영 빌드)로 돌리고 있었다. 로컬 업로드는 `public/uploads/`
에 쓰이는데 운영 빌드는 빌드 시점의 목록만 내주므로 **방금 올린 파일이 404 가 난다.**
그래도 `<img>` 태그는 DOM 에 있어서 "올린 사진이 보인다" 검사는 통과했다.

매 회차 찍히던 `콘솔 오류: ["Failed to load resource: 404"]` 가 그 흔적이었고,
나는 그걸 여러 번 보고도 지나쳤다. **검사가 매번 내미는 경고를 무시하면 검사가 없는
것과 같다.** `npm run dev` 로 돌리니 콘솔 오류 0건.

- `ui-flows` → `npm run dev` (사진을 올린다)
- `ui-audit` → `npm start` (dev 는 느려서 '느리다' 를 잘못 잰다 — 26조각)

두 스크립트 머리말에 적어 뒀다.

### 남은 무게 하나 — 가족의 사진

홈의 2.2MB 스티커는 그대로 뒀다. 가족이 올린 사진이라 내가 줄이지 않는다.
앞으로 올리는 것은 `lib/image-upload.ts` 가 브라우저에서 줄인다(앨범 2000px ·
브랜드 800px · 스티커 600px). 이미 올라간 것을 줄이려면 물어보고 한다.

그리고 흰색 뭔가 그런 느낌으로 잘 꾸민거 맞아?"**

### 무엇을 잘못 읽었나

27조각 뒤 "혁신적으로 바뀐 게 없다" 는 말에 방향을 물으면서, 내가 만든 보기에
`진한 배경 / 잡지풍 여백 / 각진 편집 레이아웃` 을 적어 넣었다. 사용자는 그 보기를
골랐고 나는 그것을 **취향의 승인**으로 읽었다. 하지만 그 문장은 내가 쓴 것이다 —
사용자가 고른 것은 "확 바꿔줘" 였지 "진한 배경" 이 아니었다.

기억에 남아 있던 것과도 어긋났다: *pastel/clean/consistent taste*. 개편 전 사이트가
이미 파스텔 + 흰색이었고, 사용자가 바란 것은 **그 결을 더 잘 만드는 것**이었다.

**사용자의 말**을 근거로 삼는다. 이번에는 그 말이 있었다 — "아기자기, 핑크 파스텔, 흰색".

## 한글이 낱말 한가운데서 끊기고 있었다

데스크톱 `/baby` 를 보다 빈 화면 안내가 이렇게 끊긴 걸 봤다:

> 오늘의 몸 상태, 병원 이야기, 아기에게 한마디. 무엇이든 **좋**
> **아요.**

브라우저 기본값(`word-break: normal`)은 CJK 를 **글자 사이 아무 데서나** 자른다.
영어에는 안 생기는 일이라 눈에 잘 안 띄지만, 한국어에서는 읽는 속도를 눈에 띄게
떨어뜨린다. 재 보니 폰 4곳 · 데스크톱 6곳이었다 — 홈 인사말, 게시판 쪽지 셋,
아기 빈 화면.

`body` 한 곳에 `word-break: keep-all` + `overflow-wrap: break-word` 를 걸었다.
뒤엣것이 짝으로 필요하다: `keep-all` 만 두면 띄어쓰기 없는 긴 주소가 판을 밀어
가로 스크롤이 난다.

**`word-break: break-word` 는 함정이다.** 레거시 값이라 `word-break` 를 `normal` 로
되돌린다. `.md-content` 가 이걸 쓰고 있어서, 게시판 **글 안의** 한글만 규칙이 풀린
채 계속 쪼개지고 있었다. `overflow-wrap` 으로만 적도록 고쳤다.

### 검사

`scripts/ui-audit.mjs` 에 넣었다. 글자 한 자씩 `Range` 를 잡아 `top` 이 바뀌는
지점을 찾고, 그 경계의 앞뒤가 **둘 다 한글이면** 낱말 한가운데서 끊긴 것이다
(띄어쓰기에서 끊긴 건 정상이므로 걸리지 않는다). 폰·태블릿·데스크톱 3폭 × 10화면.

검사가 살아 있는지 확인: `* { word-break: normal !important; }` 를 주입하니
같은 함수가 4곳을 다시 찾아냈다. 지금 CSS 로는 0곳.

## 고른 보기를 기억하지 않았다

캘린더 폰 화면은 `목록`/`달력` 을 고를 수 있는데, 들어올 때마다 `목록` 으로 돌아갔다.
달력으로 보는 사람은 매번 다시 눌러야 했다. `podong_calendar_view` 에 담는다 —
아기 기록이 작성자를 기억하는 것(`podong_baby_author`)과 같은 방식이다.

서버는 **늘 `목록` 으로 그리고** 붙은 뒤에 바꾼다. 초기값으로 읽으면 서버가 그린 것과
어긋나 하이드레이션이 깨진다.

검사는 `ui-flows` 에. **글자가 아니라 눌린 쪽(`aria-pressed`)으로 본다** — 목록 화면에도
"일" 이라는 글자가 있어서 글자로 재면 공허하게 통과한다(같은 함정을 장보기에서 한 번 밟았다).
기억을 지우면 `목록:true 달력:false` 로 떨어진다.

## 안드로이드 폭(360px)을 한 번도 안 보고 있었다

감사는 390(아이폰) · 768 · 1280 을 돌았다. 320px 로 한 번 돌려 보니 `/todos` 의
요일 칸이 **32px** 이었다 — 일곱 칸이 한 줄에 들어가야 해서 폭이 자동으로 쪼그라든다.

재 보니 경계가 딱 그 사이에 있었다:

| 폭 | 요일 칸 | |
|---|---|---|
| 320px | 32px | 미달 |
| **360px (안드로이드 대부분)** | **37px** | **미달** |
| 390px (아이폰) | 42px | 통과 |

**30px 차이가 규칙 하나를 통째로 숨기고 있었다.** 갤럭시 계열은 대부분 360 이다.

스트립을 판의 좌우 여백 밖으로 끌어내고(`-mx-4 sm:mx-0`) 칸 사이를 좁혀
(`gap-0.5 sm:gap-1.5`) 폭을 벌었다 — 320px 38px · **360px 44px** · 390px 48px.
320px 은 2px 모자라지만 일곱 칸이 서로 붙어 있고 세로가 62px 이라, 빗나가도
옆 날짜가 눌릴 뿐 바로 보이고 바로 고칠 수 있다. 여기서 더 벌리면 화면 가장자리에 닿는다.

감사 폭에 **360 을 넣었다.** 한 번 더 도는 값은 한다.

## 오류 토스트가 페이지와 같은 색이었다

겹쳐 뜨는 것들을 핑크 팔레트에서 처음 봤다. 네트워크를 끊어 오류를 내 보니
안내가 뜨긴 뜬다 — 그런데 판이 `bg-danger-soft`(#fde8e4)이고 페이지가
`paper`(#fbeaf2)다. **1.018:1.** 그림자와 1.47:1 짜리 테두리만으로 버티고 있었다.

세 가지가 겹쳐 나쁘다:

- 토스트는 **3초 뒤 사라진다.** 놓치면 실패한 줄도 모른 채 넘어간다.
- `say()` 호출이 **전부 오류다**(`grep` 으로 확인 — 성공 토스트는 한 곳도 없다).
  즉 가족이 평생 보는 토스트는 이 안 보이는 것 하나뿐이었다.
- 낙관적 업데이트를 되돌리는 자리다. 목록에서 항목이 슬쩍 사라지는데 이유를
  말해 주는 유일한 창구가 안 보인다.

`bg-danger-ink text-white` 로 바꿨다 — 페이지 **6.20:1** · 흰 판 7.17 · 틀 5.05,
흰 글자 7.17. 기본 토스트(`bg-ink`)와 같은 "꽉 찬 어두운 칩" 꼴이고 색상만 다르다.

### 같은 논리로 버튼까지 고치면 안 된다

`soft`·`danger` 버튼도 판이 흰 판에서 **1.2:1** 이다. 그런데 이건 놔둔다 —
**글자가 5.7~6.1:1** 이라 누를 것이라는 걸 글자가 말한다(WCAG 1.4.11 은 다른 단서가
있으면 면제). 옆에 `primary`(4.91:1) 꽉 찬 알약이 있어 위계도 선다.
전부 꽉 채우면 화면만 무거워지고 파스텔이 사라진다.

체크 동그라미·입력칸은 반대다 — 안이 비어 글자가 없으니 테두리(`control` 3:1)가
유일한 단서다. **"연해서 안 보인다" 를 한 규칙으로 고치지 말 것.** DESIGN.md §2에 표로 남겼다.

검사: `lib/colors.contrast.test.ts` 가 토스트 판 두 개를 **놓일 수 있는 배경 셋**
(페이지·흰 판·틀) 전부에서 3:1 이상, 흰 글자 4.5 이상, 그리고 오류/기본이 **색상으로**
20도 이상 벌어지는지 본다. `danger-ink` 를 옛 소프트 값으로 되돌리면 1.02 로 떨어진다.

## 대화 화면: 내 말풍선이 두 번째로 사라졌다

포동이 대화는 **내용이 있는 모습을 한 번도 안 봤다** — 감사는 겹쳐 뜨는 판에 닿지 못하고,
실제로 말을 걸면 가족의 ChatGPT 사용량을 쓴다. 그래서 로컬 DB 에 대화 한 판을
직접 넣어(모델 호출 0회) 폰·데스크톱에서 열어 봤다.

내 말풍선이 `bg-primary-soft`(#fce4ee)인데 대화 바탕이 `paper`(#fbeaf2)다. **1.039:1.**
풍선은 없고 로즈 글자만 공중에 떠 있는 것처럼 보였다. 포동이의 흰 카드는 1.157 —
이 판의 최소 단차다.

**이 자리가 무너진 건 두 번째다.** 처음엔 포동이의 **흰** 카드가 **흰** 시트 위에 얹혀
1.24:1 이었고, 대화 바탕을 `paper` 로 내려 고쳤다. 그러자 그 `paper` 가 이번엔
내 말풍선을 삼켰다. **한쪽을 고치면 반대쪽이 걸린다.**

`bg-chrome text-chrome-ink` 로 바꿨다 — 바탕과 1.227(최소 단차를 넘는다),
글자 8.89:1(전에는 5.73). 이제 **로즈 판 = 내 말 · 흰 판 = 포동이** 로 모양이 가른다.

검사는 두 판을 **바탕에서도, 서로에게서도** 1.15 이상 떨어져 있는지 본다.
글자 대비만 재면 옛 값도 5.73:1 로 통과한다 — **판은 따로 재야 한다.**
`chrome` 을 옛 값으로 되돌리면 1.039 로 떨어진다.

### 감사가 겹쳐 뜨는 판에 닿게 했다

대비 검사가 목록 화면만 훑고 있었다. 오류 토스트가 1.02:1 로 오래 살아남은 것도,
말풍선이 두 번 무너진 것도 그래서다. 이제 화면마다 `추가/만들기/남기기` 를 눌러
모달을 열고 **한 번 더 잰다**(입력칸 이름 검사가 이미 쓰던 방식). 네 폭 모두 통과.

## 같은 것에 하루 네 번 걸렸다 — 그래서 한 번에 쓸었다

오류 토스트(ΔE 6.4) · 내 말풍선(3.1) · 게시판 로즈 쪽지(2.9) · 캘린더 `오늘`(3.1).
전부 **연한 판을 연한 판 위에** 올린 것이었다. 한 화면씩 눈으로 찾는 대신
전부를 한 번에 재기로 했다.

### 대비로는 못 잰다

처음엔 대비(명도비)로 쟀더니 7곳이 나왔는데 **네 곳이 거짓 양성**이었다:

| | 대비 | ΔE | 실제 |
|---|---|---|---|
| 라벤더 쪽지 vs 분홍 페이지 | 1.033 | 8.4 | **잘 보인다** |
| 스카이 쪽지 | 1.002 | 11.0 | **잘 보인다** |
| 버터 쪽지 | 1.071 | 19.2 | **잘 보인다** |
| 로즈 쪽지 | 1.032 | **2.9** | 안 보인다 |

대비는 **명도만** 잰다. 라벤더와 분홍은 명도가 거의 같지만 색상이 달라 눈에는 확연하다.
로즈와 분홍은 같은 계열이라 정말 안 보인다. **같은 숫자, 다른 결과다.**
(danger 와 primary 를 색상각으로 갈랐을 때와 같은 함정이다 — 두 번째로 밟았다.)

**ΔE(Lab 거리)** 로 바꾸니 네 거짓 양성이 사라지고 진짜만 남았다.
기준선은 **9.3** — 포동이의 흰 카드가 대화 바탕에서 떨어진 만큼, 즉 이 판에서
"떠 있다" 로 보이는 최소치다. 7 아래를 잡는다.

### 판은 채움 아니면 가장자리로 정의된다

쪽지 여섯의 채움을 다 진하게 하면 파스텔이 죽는다. 대신 **그 쪽지의 기본색 테두리**를
줬다 — 페이지와 ΔE 22.7~41.2 로, 여섯 다 가장자리가 생긴다. 검사도 같은 규칙을 안다:
채움이 묻혀도 테두리가 ΔE 7 이상이면 통과시킨다.

세그먼트 트랙(`목록`/`달력`, `전체`/`일상`/…)도 `line-strong` 테두리(ΔE 12.7)를 줬다.
고른 흰 알약만 보이고 "여기 고를 게 더 있다" 는 게 안 보였다.

캘린더의 `오늘` 은 `soft` → `outline`. **`soft` 버튼은 흰 판 *안*에서만 괜찮다** —
페이지 바탕 위에 그냥 놓이면 채움이 사라져 글자만 뜬다. 옆의 ‹ › 는 흰 동그라미라
버튼처럼 보이는데 `오늘` 만 안 그랬다. 같은 묶음인데.

### 검사

`ui-audit` 에 넣었다(대비 검사와 같은 순회라 추가 비용 거의 없음, 모달 안까지).
변이 확인: 쪽지 테두리를 소스에서 떼면 로즈 쪽지가 ΔE 2.9 로 다시 잡히고,
트랙 테두리를 지우면 두 세그먼트가 3.3 으로 잡힌다. 지금은 두 폭 모두 0곳.

### 로컬에는 없는 상태가 운영에 있었다

같은 검사를 **운영 화면에** 돌렸더니 로컬에서 0곳인데 운영에서 1곳이 나왔다 —
홈의 `홈에서도 보기` 버튼(ΔE 3.1, 캘린더 `오늘` 과 똑같은 경우).

로컬 시드는 `showOnHome: true` 라 **그 버튼이 아예 안 그려진다.** 검사가 못 본 게
아니라 **그 상태가 로컬에 없었다.** 화면을 다 돌아도 상태를 다 도는 건 아니다.

그래서 이 검사는 **운영에도(읽기만) 한 번 돌린다.** 만들지도 지우지도 않고
페이지를 열어 색만 재므로 안전하다.

## 들어올 때마다 내용이 다시 스르륵 올라왔다

등장 애니메이션이 일곱 곳에 있었는데 **다섯 곳이 "페이지가 열렸으니까"** 였다 —
캘린더는 **격자 전체**, 사진첩·계획은 카드마다, 계획 상세는 섹션마다, 게시판은 쪽지마다.
`animation: ... both` 라 내용이 **투명한 채로 시작해서** 0.5초에 걸쳐 나타난다.

재 봤다. 내용이 다 보이기까지:

| | |
|---|---|
| 캘린더 | 397ms |
| 사진첩 | 408ms |
| 게시판 | 447ms |

네트워크 없는 로컬에서 그렇다. 이미 받아 둔 내용인데, 페이지를 옮길 때마다 그만큼 늦다.
LCP 도 속고 있었다 — 내용이 안 보이니 **페이지 제목**이 LCP 로 잡혔다.
걷어내니 LCP 가 진짜 내용(앨범 사진·계획 날짜·쪽지 글)으로 바뀌었다.

남긴 자리는 **무언가 도착할 때**뿐: 토스트 · 할일의 알림 줄 · 열리는 판(모달·드로어·포동이 시트).
쓰이지 않던 `--animate-float`(6초 무한 반복)도 뗐다.

`lib/motion.test.ts` 가 허용 목록을 들고 있다. 취향을 강제하는 게 아니라 **일부러 적게**
만드는 장치다 — 실제로 이 시험이 포동이 시트 하나를 내가 못 세고 지나간 걸 잡아냈다.
사진첩 카드에 도로 붙여 보면 시험이 그 파일 이름을 대며 떨어진다.

## 간판 숫자가 화면마다 다른 글꼴이었다

화면에 **실제로 그려진** 글자 크기·굵기·글꼴을 전부 모아 세 봤다(10화면, 22가지 눈금).
거기서 한 줄이 튀었다:

```
     60px  700 주아       2  8주 2일     ← /baby 히어로
     30px  700 본문       1  8주 2일     ← 홈 카드
```

**같은 "8주 2일"** 인데 한쪽은 주아 60px, 다른 쪽은 고딕 30px 이었다. 홈 카드가
`.font-num` 을 달고 있어서다 — 그건 **목록 안의 작은 숫자**(날짜·개수)용이라
일부러 고딕에 묶어 둔 클래스인데, 크게 세우는 숫자에까지 붙어 있었다.

30px 은 제목 글꼴 하한(18px)보다 한참 위라 주아가 뭉치지 않고, 한 줄짜리 숫자는
자릿수 정렬이 필요 없다. `font-display` 로 바꿨다. 이제 어디서 보든 같은 얼굴이다.

### 나머지 눈금은 그대로 둔다

크기 12가지(60·30·28·24·20·18·16·15·14·12·11·10). 작은 쪽이 촘촘하지만 각자 자리가 있고,
감사가 1.5배 확대·AA 대비를 이미 통과한다. 한 번만 쓰인 눈금 둘(15/600 = `md` 버튼,
12/500 = 장보기 접힌 줄)도 척도 안에 있다 — **숫자를 줄이려고 화면을 흔들지 않는다.**

가장 작은 글자는 하단 탭바 라벨 10px 인데, 이건 탭바의 관례이고 아이콘이 뜻을 나른다.
(글자 크기 하한은 문서에 없다. 여기가 사실상 바닥이라는 것만 적어 둔다.)

## 감사가 한 번도 안 들어가 본 화면 — 꾸미기 모드

가족이 실제로 쓰는 기능인데(홈에 스티커가 붙어 있다) 핑크 팔레트로 한 번도 안 봤다.
열어 보니 세 가지가 어긋나 있었다:

- **`사진 추가` 가 알약 안에서 두 줄로 접혔다** — "사진 / 추가".
- **`완료` 가 36px** (사이트 규칙은 폰에서 40px).
- **같은 동작을 두 이름으로 불렀다** — 상단바는 `마치기`, 툴바는 `완료`.
  둘 다 편집을 끄는 같은 동작이다.

원인은 하나였다: 툴바 버튼이 `Button` 컴포넌트가 아니라 **손으로 만든 `<button>`** 이었다.
그래서 `sm` 의 `h-10 lg:h-9` 도, `whitespace-nowrap` 도 못 받았다. `Button` 으로 바꾸고
이름을 `마치기` 로 맞췄다(한 동작은 흐름 내내 한 이름 — DESIGN.md §8).

### 검사 셋을 더 넣었다

1. **버튼 글자가 두 줄로 접히는가.** `Range.getClientRects()` 로 실제 줄 수를 센다.
   **직접 붙은 글자만** 본다 — 제목·설명이 각각 자식으로 들어간 메뉴 항목은 원래 두 줄이라
   그걸 세면 거짓 양성이 쏟아진다. 지금 화면에서 0곳, 옛 버튼으로 되돌리면 9곳.
2. **꾸미기 모드 안에서도** 접힘·대비·탭 타깃을 잰다. 같은 순회 안에서 켜고 끈다
   (`localStorage` 의 편집 상태는 끄고 나서 지운다 — 안 그러면 다음 화면이 꾸미기로 열린다).
3. **"한 번도 못 들어갔다" 를 오류로 만든다.** 꾸미기 버튼을 못 찾으면 검사가 조용히
   아무것도 안 하고 "문제 없음" 이 된다 — 오늘 같은 함정을 두 번 밟았다(운영 빌드 착각·
   로컬에 없는 상태). 이제 0번 들어갔으면 그 사실 자체가 오류다.
   버튼 이름을 일부러 틀리게 해 확인했다: `⚠ 1건 — 꾸미기 모드에 한 번도 못 들어갔습니다`.

## `keep-all` 을 걸었으니 긴 글자를 직접 넣어 봐야 했다

한글을 어절로 끊게 만들면서 **띄어쓰기 없는 긴 글자가 판을 밀 위험**을 만들었다.
`overflow-wrap: break-word` 를 짝으로 붙여 뒀지만, 그건 **추론이지 확인이 아니다.**
실제로 넣어 봤다 — 세 가지 최악을, 세 폭(320·360·390)에서.

| 넣은 것 | 결과 |
|---|---|
| 띄어쓰기 없는 한글 27자 | ✅ 멀쩡 — `break-word` 가 받아 준다 |
| 긴 쿠팡 주소 | ✅ 멀쩡 (`/` `?` `&` 가 끊을 자리를 준다) |
| 띄어쓰기 없는 영단어 61자 | ❌ **홈의 쪽지 격자가 벌어졌다** |

**`keep-all` 이 원인이 아니었다.** 격자 칸의 기본 `min-width: auto` 가 "내용의 최소 너비"
라서, 긴 단어 하나가 칸을 통째로 벌린다. `overflow-wrap` 은 **줄바꿈 규칙이지 최소 너비를
줄이지 않는다** — 그래서 이걸 못 막는다. 320px 에서 288px 칸에 538px 카드가 들어가
오른쪽이 잘렸다(가로 스크롤은 `body { overflow-x: clip }` 이 막고 있어 안 보인다).

`min-w-0` 두 곳. 그리고 **나머지 격자도 전부 재 봤다** — 앨범·기념일·할일·장보기·캘린더는
멀쩡했고 **계획 카드 하나가 더 걸렸다**(같은 이유, 320px 에서 538px). 한 번에 쓸었다.

검사는 `ui-flows` 에 넣었다. 실제로 만들고, 세 폭에서 보고, 지운다.
`min-w-0` 을 떼면 네 단계가 전부 떨어진다 — 320px 에서는 한글과 주소도 같이 걸린다.

**"짝으로 붙여 뒀으니 괜찮겠지" 를 검사로 바꾼 자리다.**
